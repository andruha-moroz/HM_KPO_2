# ПОС — Преподавательская Оценка Студентов

Учебное консольное приложение на Java 17 для ведения списка студентов, рубрикатора критериев и оценок. Проект сделан как Gradle-проект и открывается в IntelliJ IDEA непосредственно по `settings.gradle` (или `build.gradle`). В проект включён Gradle Wrapper.

## Сборка и запуск из терминала

Нужен JDK 17 или новее. Gradle Wrapper фиксирует версию Gradle 9.9.1 и скачает её при первом запуске; тестовые и coverage-зависимости загрузятся из Maven Central. JAR и дистрибутив wrapper синхронизированы с Gradle 9.9.1; SHA-256 wrapper JAR проверен по [официальному списку Gradle](https://gradle.org/release-checksums/).

Обновить wrapper при переходе на другую версию можно так:

```bash
./gradlew wrapper --gradle-version 9.9.1 --distribution-type bin
```

Запустить интерактивную консоль:

```bash
./gradlew run
```

Собрать приложение и тесты:

```bash
./gradlew clean build
```

Собрать исполняемый JAR и запустить его без Gradle:

```bash
./gradlew clean jar
java -jar build/libs/pos-student-assessment-1.0.0.jar
```

Демонстрационный сценарий доступен и через Gradle, и через JAR:

```bash
./gradlew run --args="--demo"
java -jar build/libs/pos-student-assessment-1.0.0.jar --demo
```

Демонстрация создаёт воспроизводимый сценарий в `data/demo/` и выгружает ведомость в `exports/demo_final_grades.csv`. Обычный запуск использует `data/` и экспортирует в `exports/final_grades.csv`. Данные остаются локальными в проекте и хранятся в UTF-8 CSV: `students.csv`, `criteria.csv`, `evaluations.csv`.

## Правило итогового балла

Каждая оценка переводится в долю от максимума критерия. Итог по шкале 0–10 — сумма долей, умноженных на веса, делённая на сумму весов **всех** критериев, затем умноженная на 10. Неоценённые критерии дают ноль в текущем итоге. Отдельно показывается покрытие рубрикатора по весам, поэтому частичный итог явно отличается от полностью выставленной оценки. Вес может быть любым положительным числом: значения 60 и 40 дают то же соотношение, что 0,6 и 0,4.

## DDD и ubiquitous language

Слова предметной области сохранены в именах кода: `Student` (студент), `Criterion` (критерий), `Evaluation` (оценка), `FinalGrade` (итог).

- **Entity:** `Student`, `Criterion`, `Evaluation` имеют устойчивые идентификаторы `StudentId`, `CriterionId`, `EvaluationId`. Оценка идентифицируется отдельно, а при выставлении новой оценки для той же пары студент/критерий предыдущая заменяется.
- **Value Objects:** идентификаторы, `Score` и `Weight` — неизменяемые типы-значения с проверками. Сравнение и передача балла не обходят проверку неотрицательности.
- **Инварианты:** оценка не может превысить максимум критерия; нельзя оценить несуществующего студента или критерий вне текущего рубрикатора; имя и название критерия не пустые; вес и максимум критерия положительные. Проверки сосредоточены в доменных типах и `EvaluationFactory`, а не в меню.
- **Repository ports:** `StudentRepository`, `CriterionRepository`, `EvaluationRepository` объявлены в Domain. CSV-адаптеры находятся снаружи и реализуют эти порты.
- **Domain Service:** `FinalGradeDomainService` считает итог на основе рубрикатора и оценок студента, поскольку правило использует несколько сущностей.

## Архитектура: Ports and Adapters

```text
presentation (консоль) → application (PosFacade/use cases) → domain (модель, порты, сервисы)
infrastructure (CSV, CSV export) ──────────────────────────→ domain/application ports
bootstrap (composition root, DI) собирает адаптеры и сценарии
```

Домен не импортирует консольные или файловые классы. Application вызывает порты домена и интерфейс экспорта; Infrastructure реализует эти интерфейсы. `Main` — composition root. `ServiceContainer` является singleton DI-контейнером с Service Locator под капотом: `register`/`registerInstance` объявляют поставщиков и объекты, `resolve` находит и возвращает singleton-зависимости. Composition root регистрирует граф в одном месте, а прикладные сценарии получают зависимости через конструкторы.

Папки в `src/main/java/ru/pos/`:

- `domain/model` — сущности, value objects, доменное исключение;
- `domain/port` — интерфейсы репозиториев;
- `domain/service` — фабрика оценок, доменная служба и политика расчёта;
- `application` — сценарный фасад и порт выгрузки;
- `infrastructure/csv`, `infrastructure/export` — CSV-адаптеры;
- `presentation` — консольный адаптер;
- `bootstrap` — DI-контейнер и сборка приложения.

## GoF-паттерны

- **Порождающий — фабрика (`EvaluationFactory`).** Единая проверяемая точка создания оценки проверяет максимум по критерию и добавляет время создания.
- **Структурный — Facade (`PosFacade`).** Консоль обращается к понятным сценариям вместо прямой координации хранилищ, фабрики и доменной службы.
- **Поведенческий — Strategy (`GradeCalculationStrategy`, `WeightedAverageStrategy`).** Формулу можно заменить другой политикой, не меняя `FinalGradeDomainService` и консоль.

Паттерны участвуют в рабочих сценариях; отдельные классы ради демонстрации не добавлялись.

## Тесты и роль ИИ

JUnit-тесты проверяют доменные ограничения, расчёт частичного и полного итога, недопустимую оценку, проверку критерия, а также сохранение и замену оценки через CSV-адаптеры. Ресурсы консоли и файловых потоков закрываются через try-with-resources.

ИИ использовался как инструмент реализации и подготовки структуры/документации. 

Примеры промтов:

1. Реализуй CSV-репозитории студентов, критериев и оценок и CSV-экспорт итогов. Обеспечь корректное экранирование полей, сохранение UTF-8 и закрытие файловых потоков через try-with-resources.
2. Добавь фабрику EvaluationFactory, которая проверяет балл относительно критерия, и Domain Service для вычисления взвешенного итога по шкале 0–10. Сделай расчёт сменяемым через Strategy и объясни, как Facade упрощает консольные сценарии.
3. Напиши JUnit-тесты на доменные ограничения, расчёт итога, работу репозиториев и консольный сценарий. Настрой JaCoCo и Gradle Wrapper. Подготовь README с командами сборки, запуска JAR из терминала, тестирования и просмотра отчёта покрытия.
